First Try Is the Differentiator: How LLMs Translate Python into Rust

Leo Walker · October 2026

TL;DR

Frontier labs are now using their own models to move whole codebases over to Rust. My background is mostly in data science, so I wanted to know how well these models move numerical Python, the NumPy code I write every day, into Rust.

I gave 17 models 39 numerical Python tasks to translate: 32 from NPBench, a NumPy benchmark, and 7 from Code Metal's radarlib. Every model got the same tools, reasoning effort set to medium, and up to four submissions per run. I scheduled three runs per model and task; one was lost to provider timeouts, leaving 1,988 scored runs. I graded each final answer on test inputs the model never saw.

  • Seven models reached 100% after repair. First-submission accuracy showed larger differences between models.
  • Cheaper per token isn't cheaper per task. The open-weight models wrote about 2.3 times as many tokens and needed more repairs, so on average they cost more per task than the frontier models.
  • Best value: GPT-6 Luna and Claude Haiku 5.5, with GPT-6.1 Sol the most efficient of the top-tier models. DeepSeek V4.1 Flash is the strongest open-weight model.

All the code, tasks, and results data are open source at github.com/leoalord/numpy-to-rust-eval.

1 Introduction

The question I care about is simple: does the translated code do what the original did?

With numerical code, the kind full of matrices and arrays, compiling successfully is only part of the job. Some failures are quiet: the program runs and gives you the wrong numbers. A scaling term gets dropped, two indexes get swapped, or a calculation runs at lower floating-point precision than the original. Nothing crashes, so nothing tells you it's wrong.

New models come out every few weeks, each with benchmarks from some other area. I wanted one that matches my own background. I picked NPBench because it covers a wide variety of problems, from linear algebra to physics simulations. Code Metal's work on verified code translation also interested me, and I wanted to include radar-processing tasks from their radarlib.

I compared models using the same tools and submission budget, measuring both accuracy and cost. Passing tests is evidence, not proof, so "correct" here means the Rust matches the Python outputs within the grading tolerances on inputs the model never saw.

2 Related work

TransCoder judged a translation by whether it passes tests, not by how the code looks, and that idea is the basis for building evals like this one.

Recent projects apply similar checks to whole codebases. The Bun team ported Bun, about 535,000 lines of Zig, to Rust in 11 days with Claude Code. It passed Bun's test suite and still introduced 19 regressions, since fixed. Google reports Gemini 4 Argon agents porting libraries like re2 and libgav1, and even the Fuchsia Zircon kernel, over to Rust. Both rely on the same two signals I use: compiler errors to drive repair, and outputs compared against the original.

Code Metal frames the goal as behavioral equivalence: the new code has to behave like the old code. They check it on a spectrum that runs from testing the two versions side by side all the way to formal proof. This study sits at the testing end of that spectrum.

Their type-mapping work argues that the types at a function's boundary should come from a fixed schema rather than from the model. My task contracts fix the Rust function signatures in advance. Their workflows-versus-agents paper was one of the main motivations for this project and shaped how I designed the harness.

3 Setup

3.1 The workflow

Each run is a single model working on a single task, driven by a four-node LangGraph graph.

Solid edges are the repair loop; dashed edges end a run early. Held-out results come only from the last node, so they never reach the model.

The model writes or edits a Rust file, and that file moves straight on to be compiled and tested. Each submitted version is one submission, and each run allows up to four submissions. After a failure, the model sees the compiler errors or where its values were wrong, but never the values it should have produced. The run stops when every development test passes or after the fourth submission, and that last submission is graded on the held-out cases. Just like the expected values, the held-out results are never shown to the model.

3.2 Preparing a submission

A model call is one request to the LLM. A submission can involve several model calls, but its first successful code edit sends the file straight to compile and test. The model has three tools:

Tool What it does Submits the file?
write_code Replaces the whole Rust file Yes, if it succeeds
replace_code Swaps out one block of the file Yes, if it succeeds
declare_dependencies Sets which Rust libraries (crates) to install No

A model needs to declare any dependencies before submitting code so the environment is set up before its code gets compiled. The prompt tells the models to answer with tools, and a reply without a tool call submits the file as it stands. If an edit fails, the model gets the error and can try again, up to ten model calls per submission. That cap rarely mattered: only 34 of the 2,640 submissions went forward without a successful edit. Preparing a submission took 1.16 model calls on average.

For this round I didn't give the models a search tool. They see the Python source, the Rust function signature, the starter crates, and their latest feedback, and never the grading code, a reference solution, or the expected values.

3.3 Tasks and models

  • NPBench (32 tasks) covers linear algebra, stencils (grid updates where each cell reads its neighbors), dynamic programming, FFTs, neural-net layers, and physics simulations.
  • radarlib (7 tasks) adds six synthetic-aperture radar stages plus the full Range-Doppler Algorithm, which chains two of them (range compression and RCMC) with azimuth compression.

Each task fixes its Rust signature up front, and the held-out cases include at least one input bigger than anything the model was tested on during the run.

All 17 models ran at reasoning effort medium, and each ran every task three times to reduce the influence of a single lucky or unlucky run. Seven are frontier models from OpenAI, Anthropic, and Google, called through their own APIs; the other ten are open-weight models I ran on Fireworks AI. One run was lost to provider timeouts, leaving 1,988 scored runs. The whole batch cost about $69.

4 Results

First-submission accuracy was 81.1% as recorded, or 82.7% after the starter-crate adjustment explained below. Final accuracy after repair was 95.7%. The radar tasks widened the gap mainly among models outside the top six; section 4.4 breaks down that split. Each model keeps its maker's color in every chart.

4.1 First try separates the models

After repair, seven models score 100% and fourteen score 97.4% or higher, so final scores cluster near the ceiling. First-submission accuracy shows larger differences:

Pass rate by model

Filled dot is first try, colored by provider, with a bar for its 95% interval. The ring is the final held-out rate.

Intervals resample tasks, with trials kept together. A perfect score gives a zero-width interval, which says nothing about tasks outside this set.

Each model had 117 scored runs (116 for Inkling).

The first-try figures include a starter-crate adjustment. I replayed 49 first submissions that failed to compile because a starter crate was undeclared, adding only the missing declaration and leaving the Rust code unchanged. Of those, 31 passed and count as first-try successes here. This raises the overall rate from 81.1% to 82.7%; Notes gives the affected models.

GPT-6.1 Sol and Claude Opus 5.5 got every task right on the first try. Just behind them, the smaller models, Claude Haiku 5.5 and GPT-6 Luna, are very accurate for what they cost.

Haiku beating Sonnet surprised me. Sonnet reported zero reasoning tokens in most runs. Five of its eight original first-submission failures were missing crate declarations; the adjustment fixes those five, but Haiku still finishes ahead. I can't tell from this batch whether the reasoning difference explains the gap. Gemini 4 Argon struggling on the neural-net tasks (50%) was another surprise.

It was nice to see open-weight models that are both efficient and accurate: DeepSeek V4.1 Flash scored slightly higher than GPT-6 Luna on the first try. NVIDIA's Nemotron Lightning 3.5 was underwhelming at 30.8%.

4.2 Higher spending did not consistently improve accuracy

Cost per run varies about 70-fold, from $0.0013 for GPT-6 Luna to $0.093 for Gemini 3.8 Flash, and it barely tracks accuracy.

Mean cost per run vs first-try rate

Cost axis is logarithmic. Prices are the 2026-10-19 roster; a model is on the frontier when no cheaper model has a higher first-try rate.

Plenty of models used a lot of reasoning tokens, the "thinking" a model does before it answers, without getting more accurate for it, and all that thinking adds both time and cost. Open-weight models are often cheaper per token, but they wrote about 2.3 times as many tokens and needed more submissions (1.51 on average against 1.06), so they cost more per run ($0.038 against $0.030). Kimi K3, Ember-1, and Inkling each cost more than Claude Opus 5.5 and scored 12 to 40 percentage points lower on first-submission accuracy.

GPT-6 Luna and Claude Haiku 5.5 offer the best value in this batch. Among models with 100% first-submission accuracy, GPT-6.1 Sol is the cheaper option, though it costs seven times as much as Haiku for 1.7 percentage points more. Gemini 3.8 Flash used so many tokens that it cost more than three times as much as Gemini 4 Argon, and it scored lower. DeepSeek V4.1 Flash nearly matches Argon (92.3% against 93.2%) at 40% of the cost.

4.3 "Medium" effort means different things

Every model was set to medium reasoning effort, but that means very different things from one provider to the next. GPT-6.1 Sol's median was 123 reasoning tokens per run. Claude Opus 5.5, GPT-6 Luna, and Gemini 4 Argon were also in the hundreds; Claude Haiku 5.5's median was 1,974. Gemini 3.8 Flash's median was 21,565. Median run times ranged from 13 to 159 seconds.

Models that used more reasoning tokens or took longer were not consistently more accurate in this batch. Across models, longer runs tended to score lower. Within repeated runs of the same model and task, first submissions that failed used fewer reasoning tokens up front on average than those that passed. Neither comparison establishes that changing the reasoning budget would change accuracy. I was pleasantly surprised by how quick GPT-6.1 Sol and Claude Opus 5.5 were for how accurate they were.

4.4 Difficulty sits in a few tasks

Across all models and trials, 26 of the 39 tasks have a first-submission pass rate of at least 80%. The hardest are resnet (33.3%) and scattering_self_energies (46.0%); four of the next seven are radar tasks (62.7–72.5%).

4.5 Repair fixes three in four failures

Before the starter-crate adjustment, 375 first submissions failed. Repair fixed 289 of them: 203 on the second submission, 61 on the third, and 25 on the fourth. The second submission accounted for 70% of successful repairs. Of the runs that used all four submissions, 23% passed.

5 Discussion

First-submission accuracy was the more useful way to distinguish models in this task set, since final scores clustered near 100%. For an unattended translation tool, I'd want to consider that alongside repair success and cost. The frontier models' lower average cost per run came with fewer tokens and fewer submissions.

The numerical failures are worth a closer look. In 13 of resnet's 15 final failures, the model stored a padded buffer at single precision (f32) where NumPy uses double (f64). The tests caught the resulting errors. Fixing the input and output types alone doesn't prevent that mistake: the signature stays the same while the precision changes inside the function.

I also need to improve the harness. The prompt described starter crates as "available" without making clear that they still had to be declared. Next time it should say "Starter crates are not included automatically; declare any you use." The one-edit-per-submission rule can also discard useful work: one GLM 5.3 run lost two correct follow-up edits and then broke the code again on its next submission.

Limitations and future work

  • Tests are evidence, not proof. The held-out cases only check the values they reach; Bun's port passed its full test suite and still introduced 19 regressions.
  • Correctness only. I don't measure how fast the translated Rust runs.
  • Three trials rank tiers, not neighbors. None of the top six differ from each other by a statistically significant margin.
  • One prompt, one effort setting, and no documentation search.
  • Prices and timing. Costs use the prices recorded in the October 19, 2026 model roster. All runs shared one machine, so run times include waiting and may differ on other hardware or under a different workload.
  • Next: the remaining 22 NPBench tasks, and a Rust documentation search tool (planned on Exa) to compare against this closed-book round.

Notes

Starter-crate correction. The prompt listed six starter crates as "available" without saying they still had to be declared, and 49 first submissions failed to compile for that reason alone. I replayed each one with the code unchanged and only the crate declared; 31 passed, and the first-try figures count them. Three models change: Muse Spark Open (69.2% as recorded), Claude Sonnet 5.5 (93.2%), and Inkling (57.8%).

Reasoning tokens for Claude Sonnet 5.5 and Inkling. Sonnet's median of 0 is real: with adaptive thinking at medium it chose to think in only 38 of its 117 runs (41 of 130 model calls), against 116 of 117 calls for Opus and all 120 for Haiku. LangSmith's records for every Sonnet run agree. Inkling did reason, and Fireworks returns its count, but in a field LangChain doesn't map, so neither my harness nor LangSmith recorded it; it's left off the reasoning chart. Its raw responses put the median at about 5,200 reasoning tokens per run. Costs and pass rates are unaffected, and the other nine Fireworks models' counts were recorded correctly.

How candidates are built and graded. Every candidate builds and runs in Docker with no network, a read-only filesystem, and memory, CPU, and time limits; only crate downloads touch the network. Outputs must match NumPy's shapes and types exactly, integers must be equal, and floats must agree within a relative tolerance of 1e-5 for single precision and 1e-9 for double. After a failure the model sees the error, or up to five mismatched positions, but never the expected values. A run that hits a provider error, $5 of spend, or repeated infrastructure failures ends early and isn't counted against the model.
